# PropIQ — project context for Claude

Multi-company **ERP & CRM for property dealers and housing-scheme developers in Pakistan** (PKR, CNIC, Marla/Kanal, Urdu-ready, WhatsApp-first). Sold as a subscription with three tiers (Basic / Moderate / Premium).

**Phase:** polished front-end **prototype on mock data** (no real backend yet) **plus a complete, tested production backend design**. The prototype is the client-facing demo, so UI quality matters a lot — the client is non-technical and judges by what they see.

Read these before starting a feature (in this order of usefulness):
- `docs/BACKEND_DESIGN.md` — production architecture, the decisions behind it, module-by-module data model, security, scaling, free-tier hosting, roadmap, open questions.
- `docs/erd/viewer.html` (open in a browser) / `docs/erd/ERD.md` — the data model as diagrams (**231 tables, 15 feature areas; 155 MVP / 76 phase-2** — every module declares `phase` in `schema.mjs`, the build fails without it).
- `docs/HARDENING_REVIEW_AND_SPEC.md` — which review findings were real (and which were already solved), the spec plan, and the **progress log** (what is done, what is next).
- `docs/STATE_MACHINES.md` — the legal status changes per record type (enforced by the database).
- `docs/FEATURES.md` (tier matrix), `docs/DESIGN_GUIDELINES.md`, `docs/CONTEXT.md`, `docs/TECH_STACK.md` (older prototype-stage docs; the backend doc supersedes them where they differ).

## Backend (`api/`) — Fastify over Supabase Postgres

Decisions (2026-10-09): customers are **housing-scheme developers** first (broker/commission work deferred); host **Supabase** (Postgres + Auth + Storage); login **Supabase Auth**; the API verifies its tokens. The API is deliberately thin — business rules live in `docs/schema/core.sql`; the API sets who is asking (`app.user_id`, `app.company_id`, `app.permissions`, `app.request_id`, transaction-local) and translates database errors into plain messages. It connects as the restricted `propiq_app` role, never the owner. See `api/README.md` (setup, request flow, endpoints).

| Task | Command |
|---|---|
| API tests (114, in-memory Postgres over a real connection) | `cd api && npm test` |
| Whole app offline (DB + API + sign-in stand-in, seeded with ByteCraft) | `cd api && npm run sandbox`, then run the website with the env vars it prints |
| Browser end-to-end tests (`run.mjs` 26 checks, `finance.mjs` 21, `sales.mjs` 12, `modules.mjs` 27, `features.mjs` 15, then `language.mjs` 19; run in that order on a fresh sandbox) | `cd e2e && npm install && npm test` against a fresh sandbox + website |

`core.sql` is migration `0001_core` and is now **frozen** (it is applied on the Supabase project): every schema change is a numbered file in `api/db/migrations/` (the smoke test applies core + migrations, so it always matches production). Currently `0002` (sizes, company defaults, block-in-project), `0003` (banks catalog of 43 Pakistani banks, bank accounts, 85-account chart seed, `app.ensure_period`), `0004` (voucher engine: CPV/CRV/BPV/BRV/JV/CV/SV/PIV/CN/DN, `app.approve_voucher`/`void_voucher`), `0005` (bank statements + reconciliation), `0006` (trial balance / ledger / party statement functions), `0007` (customer receipts: `app.record_receipt` posts Dr cash/bank, Cr Customer Advances, allocates to installments oldest-first; `v_receipts`), `0008` (invites + `app.company_plan`, CRM leads, quotations that become bookings, post-dated cheques, service invoices with posting, contracts, extra ledger accounts), `0009` (staff, leave, payroll that posts), `0010` (contractor agreements and bills with retention), `0011` (budget/revision self-approval setting), `0012` (extra seats), `0013` (collection reminders log, audit on team changes), `0014` (file attachments kept in the database, 4 MB each, per-company isolated), `0015` (late-payment charges, refunds on cancellation, booking transfer, dealer commission; `app.record_receipt` now pays open late charges first), `0016` (`users.preferred_language`; the company default language lives in `companies.settings`). **Every migration that creates a view must end with `select app.secure_views();`** (views must be `security_invoker`, or the owner role bypasses RLS). The root `tsconfig.json` excludes `api/`. Never import from `api/` in the Next.js app; the front end talks to it over HTTP (`lib/services` is the seam).

## Languages (8: English, Urdu, Pashto, Chinese, French, German, Japanese, Arabic)

Brief and phase plan: `docs/I18N_IMPLEMENTATION_PROMPT.md`. Term choices per language: `docs/I18N_GLOSSARY.md`. Every translation is AI-written and **needs native review** before customers see it: `docs/I18N_REVIEW.md` lists the files and the known risks. English is the default and the source of truth (the e2e tests assert English text).

- **Dictionaries:** `lib/i18n/messages/<lang>/<area>.ts` (areas: `common`, `nav`, `shell`, `auth`, `account`, `dashboard`, `admin`, `files`, `projects`, `properties`, `customers`, `deals`, `sales`, `vouchers`, `finance`, `people`, `administration`, `site`, `output`), each file a flat `"area.key": "text"` object; `<lang>/index.ts` merges them. `en` is typed; every other language is declared `Record<keyof typeof en…, string>`, so a missing key fails `tsc`. `node scripts/check-i18n.mjs` also fails on a missing/extra key or a `{placeholder}` that differs from English.
- **Using it:** `const t = useT()` (or `useLanguage()` for `lang`, `dir`, `setLanguage`) in a component; `translate(key, vars)` from `lib/i18n/runtime.ts` in code that is not a component (toasts, the insights engine, auth errors). `t("area.key", { name })`; counts use a plural group in the message: `"{count, plural, one {# item} other {# items}}"` (Arabic needs `one two few many other`). Never build a sentence from translated fragments, and never change stored status codes: map them with `t("status." + code)`; for a label built from a stored code that may be unknown use `tOr(t, key, fallback)` (`lib/i18n/runtime.ts`). Stored values (project types, document categories, receipt methods) stay English in the database and are shown through keys such as `projects.type.<value>`, `files.cat.<slug>`, `deals.method.<value>`.
- **Adding a string:** add the key to `messages/en/<area>.ts`, then to the same file of the 7 other languages, run `npx tsc --noEmit && node scripts/check-i18n.mjs`. **Adding a language:** `lib/i18n/config.ts` (`LANGUAGE_CODES`, `LANGUAGES`), `api/src/languages.ts` (a test fails if the two lists drift), `lib/i18n/load.ts`, the DB check in a new migration, the font rules in `app/globals.css`, a dictionary folder.
- **Which language shows:** the signed-in person's saved choice (`users.preferred_language`, `PATCH /v1/me {language}`; `null` clears it) → their company's default (`companies.settings.default_language`, set under Administration → Company Profile) → this browser's `propiq-lang` cookie → English. The browser language is not used. The layout reads the cookie on the server and renders `<html lang dir>` and the language's dictionary straight away, so there is no flash of English; `LanguageProvider` then reconciles with `GET /v1/me`. Because of that, every route is rendered on demand (not prerendered).
- **Right to left (Urdu, Pashto, Arabic):** use **logical** Tailwind classes only (`ms-/me-`, `ps-/pe-`, `start-/end-`, `text-start/end`, `border-s/e`, `rounded-s/e`); a mirrored icon gets `rtl:-scale-x-100`; slide animations use `useSlide()` instead of a fixed `x: -12`; direction-dependent Radix props (tooltip/menu `side`) read `dir`. Keep money, codes, phone numbers and emails left to right: `formatPkr`/`formatMoney` already wrap their result in an isolate on RTL screens; for other runs use `<Ltr>` (`components/ltr.tsx`) or `<bdi dir="ltr">`.
- **Numbers and dates:** Western digits and the Gregorian calendar in every language; money always "Rs" with the same grouping (only Urdu's compact form reads lakh/crore). `lib/format.ts` reads the language through `lib/i18n/runtime.ts`, so call sites do not pass a locale.
- **Fonts:** Latin stays Plus Jakarta Sans / Fraunces; Urdu, Pashto and Arabic use Noto Naskh Arabic (next/font, not preloaded); Chinese and Japanese load a Google Fonts stylesheet only when that language is on screen (`FONT_STYLESHEETS`), with system fonts as the fallback. Arabic-script text gets no letter-spacing (it breaks joined letters).
- **Not translated:** anything a person typed, account and bank names, demo data, the brand name, document/property codes, stored enum values. Server error messages stay English in the API; `ApiError` (`lib/api/client.ts`) shows `err.<code>` in the language on screen for codes with one fixed meaning (English keeps the server's own, more specific sentence; codes whose message carries a name or amount, such as `over_budget`, `plan_limit`, `validation`, keep the server text).
- **Printed documents** (`/print/...`) follow the interface language. **Amount in words** (`lib/amount-words.ts`) is real Urdu (lakh/crore system) when Urdu is on screen and English words in every other language. **Collection reminders** have their own language picker (all 8, default Urdu), independent of the interface: templates are `reminder.due` / `reminder.late`. The tab title is the page title in the current language (`PageHeader`, `generateMetadata` in `app/layout.tsx`); `app/not-found.tsx` and `app/error.tsx` are translated.
- **Phases:** 1 foundation + shell + auth + account + dashboard (done); 2 core modules: projects, properties (+detail), customers, deals & bookings (+detail, receipts, refunds, transfers, commissions, collections) and the shared dialogs/pickers/attachments (done); 3 the rest of the live screens, landing page, billing, settings, plot map (done, awaiting review); 4 printed documents, amount in words, reminders, error codes, page titles, 404/error pages (done, awaiting review). 5 demo-mode (sample data) screens: CRM, quotations, invoices, cheques, contracts, vouchers, accounts, expenses, budgets, reports, staff, payroll, leave, contractors, group overview, administration and their dialogs (area `demo`, keys `dm.*`; stored English labels such as budget modes or leave types go through `tx(text)` → `dm.x.<slug>`) (done, awaiting review). Still English everywhere: sample-data names, budget category templates, bank names, database role and leave-type names.

## Live mode (sign-in + real data) vs demo mode

The website runs in two modes. **Demo**: built-in sample companies and mock data (client presentations; also the only mode when `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` and `NEXT_PUBLIC_API_URL` are unset). **Live**: a person signs in (`/login`, Supabase Auth via `lib/supabase.ts`), their real companies come from `GET /v1/me`, and connected screens read/write through the API (`lib/api/client.ts`, `lib/api/live.ts`). `useAuth()` (`lib/providers/auth-provider.tsx`) gives `status` (`loading | signedOut | live | demo`); `useCompany().live` says which mode a screen is in. Real company ids are uuids (`isLiveCompanyId`); the services in `lib/services` branch on that.

- **Connected screens** (`lib/live-routes.ts`, `CONNECTED_ROUTES`): see "Live vs demo screens" below. A real company's sidebar and ⌘K list **only connected pages** (`navAvailable` in `lib/plan.ts`); the demo lists everything. **Connect a screen by adding its route to `CONNECTED_ROUTES`**, building its live component, and wrapping the page file.
- Live mode hides demo-only widgets (cash pill, notifications, plan switcher, Group Overview; `demoOnly` in `NAV_ITEMS`). Never show demo data to a signed-in real company.
- Creation dialogs use `FormDialog`, whose `onSubmit` may return a promise (waits for the server, shows the error inside the dialog). Live branch: call the API, then `queryClient.invalidateQueries`.
- Add a first real person/company with `cd api && npm run setup` (reads `api/db/setup.bytecraft.json`, not committed).

## How data flows (the seam a real backend replaces)

```
lib/mock-data/*.ts            seeded, deterministic base records ("Company 1")
  └─ lib/mock-data/company-data.ts   getDataset(companyId): derives/filters per company; getTrends()
       └─ lib/services/index.ts      xService.list(companyId)  → simulated 350 ms latency  ← replace with real API calls
            └─ lib/hooks/use-data.ts     useXxx() = useCompanyQuery("key", service) → React Query
                 └─ pages / components   read hooks; mutate with queryClient.setQueryData(["key"], …)
```

- **Multi-company is built in.** `lib/providers/company-provider.tsx` holds the active company (`useCompany()`; persisted in localStorage; `?company=co-2` deep-links). `lib/providers/query-provider.tsx` keeps **one QueryClient per company**, so cached/edited records never leak between companies and query keys stay plain (`["units"]`, `["budgets"]`). The dashboard `<main>` is re-keyed by company id so every page remounts. Seeded companies: `co-1` (original data), `co-2`, `co-3` (derived: renamed projects/people/cities, scaled money, project subset). Companies created at runtime start **empty or with sample data** (the New Company dialog offers both, sample is the default; sample companies have ids ending `-sample` and are derived like `co-2`).
- `company-data.ts` derives other companies by transforming the base data: ids matching `/^[a-z]+(-[a-z]+)*-\d+$/` get a company prefix; numbers under keys containing `amount|price|balance|salary|budget|total|value|paid|cost|fee|rent|advance|loan|commission|debit|credit` are scaled; people/project/city names are remapped. **Name money fields accordingly** (e.g. `budgetAmount`, `actualAmount`) or they won't scale. Child records with `projectId/unitId/dealId/customerId/budgetId` are cascade-filtered — add a new foreign-key field there if you introduce one.
- **Never import mock arrays directly in UI** — go through a hook. Exceptions that exist: `MOCK_TODAY_ISO` (seed.ts) and `getTrends`.
- Demo "today" is `MOCK_TODAY_ISO` = **2026-09-20**; seeded dates are offsets from it (`dateOffset`). Dashboard analytics use it so overdue/upcoming figures are stable. Budget fiscal year in the demo: `FY2026-27`, 3 months elapsed (`BUDGET_ELAPSED_MONTHS`).
- Plan tier (`lib/providers/plan-provider.tsx`, default `premium`, switchable in the top bar) gates nav items via `minTier` in `lib/plan.ts`. The sidebar lists **only the pages the plan includes** plus one "More features +N" entry (`navForTier`); the ⌘K palette still lists everything with a lock. **Basic must stay at ≤10 sidebar items** — tier a new page accordingly.
- **No false zeros:** `AnimatedNumber` renders its final value on the server and only replays the count-up after hydration; anything that depends on loaded data (hero banner, KPIs) must show a skeleton/placeholder until the data arrives, never `0`.

## Adding a feature — checklist

1. **Types** in `lib/types.ts` (keep money field names scaling-friendly, see above).
2. **Mock data** in `lib/mock-data/<thing>.ts` (use `mulberry32`/`seed.ts`; deterministic — never `Math.random()` at module level or hydration breaks). Export from `lib/mock-data/index.ts`.
3. **Company scoping:** add the array to `BASE` and `emptyDataset()` in `company-data.ts`; add any new FK field to `cascade()`.
4. **Service + hook:** `lib/services/index.ts` (`list: (companyId) => withLatency(getDataset(companyId).x)`) and `lib/hooks/use-data.ts` (`useCompanyQuery`).
5. **Navigation & permissions:** `NAV_ITEMS` in `lib/plan.ts` (section, `minTier`); add a module to `PERMISSION_MODULES` in `lib/permissions.ts` and sensible grants in `lib/mock-data/roles.ts`. The ⌘/Ctrl+K palette builds itself from `NAV_ITEMS`.
6. **Page** at `app/dashboard/<route>/page.tsx` (`"use client"`): wrap in `mx-auto max-w-[1400px] space-y-5`, start with `<PageHeader icon eyebrow title description actions />`, then KPI strip, then content. Loading = `Skeleton`; empty = designed empty state, not a blank table.
7. **Create/edit dialogs** use `components/dialogs/form-dialog.tsx` (`FormDialog`, `Field`, `FieldRow`); on submit `queryClient.setQueryData([...])` and `toast.success(...)`.
8. **Backend docs (keep them in sync):** add/adjust tables in `docs/erd/schema.mjs` (new module ⇒ declare `phase`) → `node docs/erd/build.mjs`; if the feature has database rules, add them to `docs/schema/core.sql` **with tests** in `docs/schema/smoke-test.mjs`; describe it in `docs/BACKEND_DESIGN.md` (+ its appendix lists). In `core.sql` also: every cross-reference to another tenant table goes in the `links` list of the *cross-tenant reference protection* block (check `v_tenant_fk_gaps`); a status lifecycle gets rows in `state_transitions` + a diagram in `docs/STATE_MACHINES.md`; a new document/master table is registered in `v_convention_gaps`; business-relevant tables get the `app.audit_row` trigger.
9. **Verify:** `npx tsc --noEmit`, `npx eslint app components lib`, `npx next build`; look at it in a browser (or headless Chrome: `chrome --headless=new --window-size=1440,1500 --virtual-time-budget=12000 --screenshot=out.png URL` — counters and charts are still mid-animation in such screenshots, that is expected).

## Domain decisions already made (don't relitigate without asking)

- **"Properties", not "Units".** User-facing text, nav and route (`/dashboard/properties`) say Properties; codes are `PRP-1042`. Internally the type is still `Unit`, hook `useUnits`, query key `["units"]`, file `new-unit-dialog.tsx` — leave those names.
- **Chart of Accounts *and* Vouchers are both kept** — COA is the structure, vouchers (CPV/CRV/BPV/BRV/JV) are documents that post to **one double-entry journal**. Only the prototype's stand-alone cash-book is retired in the backend design.
- **Taxes are admin-configured data** (tax codes, effective-dated rates, bundles, assignment rules, exemptions, returns) — never hard-code rates. Accountant must confirm real rates.
- **Combined transactions** = (a) within a company: one event settling several documents, split tenders, contra; (b) across companies: inter-company transactions + consolidated statements. *(Interpretation — the client's answer was short; confirm if it matters.)*
- **Budgets:** project (lifetime) + operating (fiscal year, monthly phased). Actual comes from the ledger, committed from open commitments; approved lines change only via maker-checker **revisions**; control mode none/warn/block.
- Fiscal year **July–June**; land sizes stored as entered **and** normalized sq ft (marla→sqft is a company setting; mock uses 272).
- Property model is deliberately richer than Zameen.com (legal/title, ownership chain, encumbrances, valuation, utilities, listings…) — 35 tables in the ERD.

## Backend design (production) — essentials

- **Postgres**, shared schema, `company_id` on every row, **row-level security** (`SET LOCAL app.company_id`), organization → company hierarchy, UUID ids, `NUMERIC(18,2)` money, posted ledger rows append-only (reversals only), `version` column for optimistic locking, maker-checker on approvals.
- `docs/schema/core.sql` is executable (95 tables + 4 views + 51 `app.*` functions): tenancy, RBAC, audit, numbering, journal + balance trigger, vouchers, parties, projects, the full property model, bookings/installments/receipts (split tenders, multi-target allocation), combined transactions, tax engine (`app.apply_tax_group`), budgets (`v_budget_line_status`, `app.check_budget`, revisions), inter-company posting and consolidation (`app.post_intercompany`, `app.run_consolidation`). Wave 1 hardening added: append-only receipt allocations + `app.void_receipt`/`app.reverse_entry`, property holds and derived status (`app.place_hold`, idempotent `app.create_booking`), payment schedules that must add up (`app.build_schedule`), table-driven state machines with per-transition permissions, company-checked foreign keys, keyed-hash CNIC (`docs/schema/cnic.mjs`), audit trail, branches/teams/data scope (`app.user_in_scope`), and `v_reconciliation` (9 self-checks that must be empty).
- ERD source of truth is `docs/erd/schema.mjs` (modules → tables → columns; `fk=table`, `null`, `uq`; sub-diagrams in `SUBGROUPS`). Outputs are generated — **don't hand-edit** `ERD.md`, `erd.dbml`, `viewer.html`.
- Quoting trap when scripting edits: in `String.prototype.replace` a replacement containing `$$` collapses to `$` — use slice/concat or a replacer function for SQL.

## Live vs demo screens

`useCompany().live` is true for a real (uuid) company. Live screens are separate components in `components/live/*` fed by `lib/api/finance.ts` + `lib/hooks/use-live.ts` (query keys start with `"live"`); the page file wraps the old demo page as `Demo…` and picks one. Wired to real data: **every page except Settings/Billing and Group Overview** — Dashboard, Projects, Properties, Plot map, Deals & Bookings (+ detail), Leads, Quotations, Sales Invoices, Service Invoices, Post-dated cheques, Contracts, Contractors, Vouchers, Accounts, Bank Reconciliation (live-only), Expenses, Budgets, Reports, Customers, Staff, Leave, Payroll, Administration (users + invites, roles, company profile). Inviting someone: an admin enters their email; the person creates their own sign-in (sign-up on `/login`) and joins automatically on first sign-in (`app.accept_invites`). API routes: `api/src/routes/*` (bookings, receipts, dashboard, expenses, vouchers, banking, accounting, parties…). Deployment and the go-live checklist: `docs/GO_LIVE.md` — website and API both deploy on Netlify (`netlify.toml`; the API is a Netlify Function built by `cd api && npm run build:function` from `netlify/functions-src/api.mts` via `api/src/handler.ts` + `api/src/bridge.ts`, served at `/api`, so `NEXT_PUBLIC_API_URL=/api`). `api/src/server.ts` and `api/Dockerfile` remain for a normal server. Money is a string end to end; live screens use `formatMoney` (always shows paisa), never `formatPkr`.

## Known gaps / good next steps

- **Not yet live (hidden from real companies):** Settings/Billing (plans are changed by PropIQ support for now), Group overview (multi-company consolidation). Attendance, automatic WhatsApp/SMS sending (reminders open WhatsApp with the message ready and log it), real .xlsx export (CSV opens in Excel), tax screens and a report builder are not built.
- **Documents and output:** printable pages live at `/print/[kind]/[id]` (receipt, voucher, service-invoice, booking, statement, quotation, contract, payslip; `components/live/print-docs.tsx`; the browser's Save as PDF makes the PDF). `ExportButton` (`lib/export.ts`) downloads what is on screen as CSV. Files attach to records through `AttachmentsButton`/`AttachmentsPanel` (`/v1/attachments`). Property detail: `/dashboard/properties/[id]`. Activity log: `/dashboard/administration/activity`. Password reset: `/reset-password`; account page: `/dashboard/account`. CORS must list every HTTP method the screens use (a test guards this).
- The executable migrations for CRM, quotations, cheques, contracts, staff/payroll and contractors are lean versions; `docs/erd/schema.mjs` still shows the larger phase-2 design for them (the ERD has not been regenerated for 0003–0011).

- **Designed but no UI yet:** property detail screens (specs, amenities, legal, ownership, valuation, media, listings), Tax settings (codes/rates/bundles/rules), combined-transaction & split-tender receipt screens, inter-company transaction screen, budget revision/exception flows beyond toasts, document attachments, notifications center, report builder.
- **Prototype shortcuts to replace with real backend:** all data is in-memory and per-browser; approvals/toasts are simulated; WhatsApp/PDF/exports are mocked; auth doesn't exist; Group Overview reads base datasets (not session edits).
- Open client questions are listed in `docs/BACKEND_DESIGN.md` §14 (revenue-recognition policy, budget default control mode, inter-company needs, offline use, hosting residency…).

## Working agreements

- Keep user-facing language plain and non-technical; the audience is a property-business owner.
- Prefer data-driven UI over hard-coded numbers — every dashboard figure must trace to records (see `lib/dashboard-insights.ts`).
- Don't add dependencies casually; the stack above is intentional.
- Update the docs/ERD/SQL whenever a feature changes the data model, and re-run `build.mjs` / the smoke test.
